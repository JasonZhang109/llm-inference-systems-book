# 大模型推理系统工程：性能、诊断与优化

> 从一次请求的完整路径，讲到容量规划与单位成本：把「为什么慢」拆成可测量、可验证、可复现的问题。

**18 章 · 61 张图 · 45 条证据缺口逐条核对 · 正文 CC BY 4.0**

---

## 这本书在讲什么

大模型推理服务的性能问题，很少是「模型不够快」这一个原因。更多时候是几个数量级不同的东西缠在一起：
KV Cache 的字节数、HBM 带宽、批处理的排队、多卡通信的拓扑、调度器的策略、以及你到底在为什么指标优化。

这本书按「一次请求从进到出」的真实路径组织，把每一层的账算清楚：

- **算得出来**：给定模型、精度、序列长度和硬件规格，先用 roofline 与显存账本算出「理论上该多快」，再谈优化。
- **测得到**：TTFT、TPOT、吞吐、P99 各自的定义与互相牵制，以及压测怎么设计才不失真。
- **判得准**：一次只改一个变量，用受控实验证伪自己的瓶颈假设，而不是凭直觉调参。
- **算得清**：从设备小时到每个有效完成 token 的成本，以及技术改善怎么换成可兑现的成本变化。

## 它和别的资料有什么不同

**1. 每个数字都能追到出处。**
全书 59 条登记来源（v0.8 轮 30 条第三方来源 + v0.10 轮 29 条官方文档与发布说明），逐条带版本号（tag / commit / 文档版本号）与检索日期。正文里每个引用都落到具体编号，例如 `[S02]`、`[N09]`。

**2. 明确区分「标称峰值」「第三方实测」「推导」。**
厂商规格页上的数字是**峰值理论值**，不和实测值混用；发布说明写「支持」不等于「有效果」，正文会把这句话写出来。这是本书最刻意避免的两类失真。

**3. 图表可复现。**
61 张图不是截图，而是由仓库里的脚本从本地 `figure_catalog_vNN.json` 重绘出来的。每张图的数据点、条件、边界、来源都登记在 catalog 里，改一个数就能重画。

**4. 缺口如实登记，不假装补齐。**
v0.10 轮把 45 条证据缺口逐条对照公开资料：**31 条已补齐**、**11 条只能补到机制层**（环境相关的量值必须在目标环境实测）、**3 条公开资料根本不含**（设施侧数据或需自有资源账本）。逐条对照表在 [`book_support_v10/证据缺口补齐对照_v0.10.md`](book_support_v10/证据缺口补齐对照_v0.10.md)。

## 复现图表

每张图都由仓库内的脚本生成，不联网、不调用模型：

```bash
python book_support_v08/code/replot_v08.py     # 例：重绘 v0.8 轮的 16 张第三方图
```

数值只从同目录的 `figure_catalog_vNN.json` 取（单源），所以「图与数据不一致」在结构上不会发生。
需要 Python 3 与 matplotlib；中文字体脚本会自动探测（`Arial Unicode MS` / `Heiti`，找不到则退回 sans-serif）。

## 已知边界

诚实地说清楚这本书**没有**做什么：

- **不含作者自建集群的实测数据。** 所有数值来自第三方公开数据、官方规格与工程推导。想看「某卡在某拓扑下的真实带宽」，必须在你自己的环境复测。
- **厂商规格一律标注为峰值理论值**，不与实测混用；发布说明的「支持」不等于「有效果」。
- **仍有 14 条口径未能闭合**（11 条部分补齐 + 3 条公开资料不含）。它们需要自有资源账本或设施侧数据，公开资料补不到，书中如实写明而不是留一个「待补」。
- **版本有保鲜期。** 涉及具体版本行为的结论都标了检索日期，框架迭代后请以当时的发布说明为准。
